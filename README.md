## 📢 Toast 메시지 시스템 (커스텀 알림 컴포넌트 직접 설계 및 구현) (팀장)

> 사용자에게 피드백을 주는 방법은 다양하지만, **알림(alert)**은 UX에서 매우 중요한 역할을 합니다.
> 
> 
> Pixterest에서는 기본 alert/modal을 대체할 수 있는 **직접 설계한 toast 시스템**을 개발하여 사이트 전역에 적용했습니다.
> 

---

### 🎯 도입 배경 및 목적

- 기존 `alert()` 사용 시 디자인 일관성 부족, UX 방해 요소 발생
- 사용자 흐름을 **방해하지 않는 안내 방식** 필요
- 다양한 상황(정보, 경고, 오류 등)에 맞는 **유연하고 확장 가능한 알림 시스템** 구현

---

### 📐 시스템 구성 및 설계 포인트

- `toast()` 와 `toastAlter()` 두 가지 함수로 분리하여 사용성 명확화
- 메시지 내용, 타입, 버튼, 지속 시간 등 **동적 파라미터**로 설정 가능
- 전역 적용을 위해 **Thymeleaf Fragment**로 컴포넌트 구성
- **메시지 중복 방지**, **자동 사라짐**, **버튼 클릭 기능** 등 다양한 UX 요소 반영

| 유형 | 위치 | 용도 | 특징 |
| --- | --- | --- | --- |
| ✅ toast() | 오른쪽 하단 | 일반 안내 (정보, 성공 등) | 자동 사라짐 / 사용자 흐름 방해 없음 |
| ⚠️ toastAlter() | 상단 중앙 | 경고 메시지 (보안, 오류) | 강한 시각적 알림 / 페이지 이동 유도 |

---

### ⚙️ 핵심 기능 요약

- ✅ **디자인 커스터마이징** (Tailwind + 아이콘 활용한 Modern UI 적용)
- ✅ **자동/수동 닫기 동시 지원**
- ✅ **중복 호출 방지** (동일 메시지 반복 생성 제한)
- ✅ **버튼 삽입 가능** (페이지 이동 등 사용자 액션 유도)
- ✅ **페이지 이동 후에도 메시지 유지**
    - `sessionStorage` 방식
    - `URL 파라미터` 방식 (`?alert=forbidden` 등)

---

### 🧩 예시 상황별 처리 전략

| 상황 | 사용 함수 | 이유 |
| --- | --- | --- |
| 로그인 필요 | `toast()` | 단순 안내 / 흐름 유지 |
| 저장 완료 | `toast()` + 버튼 | 동적 액션 유도 |
| 세션 만료 | `toastAlter()` | 재로그인 유도 / 경고성 |
| 권한 없음 | `toastAlter()` | 사용자 제어 차단 필요 |

### 🧠 기술 구현 포인트

### ✅ sessionStorage 방식

- 저장 후 reload 시 메시지 유지
- `window.onload`에서 값 체크 후 메시지 실행

### ✅ URL 파라미터 방식

- Controller → `redirect:/user/login?alert=forbidden`
- JS에서 URL 파라미터를 읽고 toast 메시지 출력

```jsx
const params = new URLSearchParams(location.search);
if (params.get("alert") === "forbidden") {
  toastAlter("접근 제한", "이용이 제한된 계정입니다. 관리자에게 문의하세요.");
}
```

## 🔧 트러블슈팅

---

### 🧱 z-index / position 충돌 문제

**문제점:**

- 헤더, 핀 작성 페이지, 팝업들이 겹치는 상황에서 input의 hover가 먹지 않거나 팝업이 뒤로 숨겨지는 문제 발생.

**해결:**

- 레이어 구조를 분리하고 각 요소별 `position`과 `z-index`를 명확하게 지정함.
    - header (fixed, z-index: 2000)
    - 핀 작성 페이지 (absolute, z-index: 1000)
    - 일반 팝업 (fixed, z-index: 3000)
    - 모달 팝업 (보드 생성 등) (fixed, z-index: 4000)
    - toast 메시지 (fixed, z-index: 9999)
- 팝업은 DOM 상 구조도 분리하여 충돌 방지.

**회고:**

- 단순히 z-index만 조절한다고 해결되지 않으며, position 속성과 구조(부모 요소의 context)까지 고려한 전체 레이어 설계가 필요함을 실감.

---

### 📍 팝업 위치 계산 오류

**문제점:**

- 핀 작성 시 보드 선택 팝업을 버튼 기준 위치에 띄우려 했지만, 화면 밖으로 벗어나거나 위치 계산이 어긋나는 현상 발생.

**해결:**

- 버튼 기준 위치 계산에서 좌측으로 500px 이동하는 시도를 했지만, 좌측 화면을 벗어나 발생한 문제였음.
- 위치 계산을 동적으로 하지 않고, 고정된 `left`, `top` 값을 설정하여 원하는 위치에 정확히 배치함.

**회고:**

- 동적 계산보다 안전성과 유지보수성을 위해 위치를 고정하는 방식이 더 효과적인 경우도 존재.
- 사용자 화면 크기에 따라 위치가 달라질 수 있는 요소는 반드시 예외 처리를 포함해 구현해야 함.

---

### 📌 Masonry + imagesLoaded 라이브러리 적용 실패

**문제점:**

- Masonry 레이아웃 적용이 되지 않음. gutter가 무시되거나, 이미지가 겹치는 현상 발생.

**해결:**

- CDN을 통해 `masonry-layout`과 `imagesLoaded`를 전역 등록하여 사용.
- `percentPosition: true`, `columnWidth: '.grid-sizer'` 설정과 함께 `.grid-sizer`의 width를 %로 조절.
- 이미지가 모두 로드된 이후에 `layout()` 실행되도록 `imagesLoaded` 연동 처리.

**회고:**

- 문서에 있는 예제 그대로 가져오는 것이 아닌, 프로젝트 구조에 맞게 환경 설정과 마운트 타이밍을 조절하는 능력이 필요.
- 라이브러리를 적용할 때는 HTML 구조, CSS 설정, JS 초기화 시점이 완벽히 맞아야 작동함.

---

### 🖼️ 보드 커버 이미지 undefined 문제

**문제점:**

- 보드 선택 팝업에서 커버 이미지가 렌더링되지 않고 `undefined`가 출력됨.

**해결:**

- 원인 ①: MyBatis Mapper XML에 `coverImage` 필드를 누락 → 추가하여 문제 해결.
- 원인 ②: `coverImage`가 없는 보드도 있었음 → JS에서 삼항 연산자를 사용해 디폴트 이미지로 처리.
- 원인 ③: 디폴트 이미지가 작게 출력됨 → `default-img` 클래스 분기 적용하여 별도 스타일링(중앙 정렬, 사이즈 보정 등).

**회고:**

- 데이터 흐름(쿼리 → XML → 서비스 → 컨트롤러 → JS)을 전체적으로 따라가며 확인해야 빠르게 문제를 해결할 수 있음.
- UI 예외 상황(빈 값, undefined)에 대비한 설계와 예외 스타일링은 사용자 경험에 직접적인 영향을 준다는 걸 체감.

### 📌 핀 중복 저장 문제

**문제점:**

- 동일한 핀을 여러 번 저장할 수 있어, DB에 중복 핀이 쌓이는 문제 발생.

**해결:**

- 기존에는 핀을 복사해서 새로 생성 → 중복 허용됨.
- `pin_user_save` 테이블을 별도 구성하여 저장 관계만 기록.
    - 저장 요청 시, `user_email + pin_id` 조합으로 중복 여부 확인.
    - 중복 저장 시 서버에서 차단 처리.

**회고:**

- 클라이언트와 서버 간 ID 기반 식별 및 중복 방지 로직의 중요성을 다시 인식.
- 복사본 관리가 필요한 기능은 실무에서도 자주 등장하므로, **참조 테이블 방식 설계** 경험이 의미 있었음.

### 🔁 toast 메시지 새로고침 후 유지 문제

**문제점:**

- 페이지 새로고침 시 toast 메시지를 띄우고 싶었으나, `location.reload()` 이후 JS 흐름이 초기화되어 toast 실행 불가.

**해결:**

- `sessionStorage`를 사용하여 상태를 유지.
    - toast를 띄우기 전 `"showToast": "true"` 저장
    - 새로고침 후 JS에서 `sessionStorage.getItem()` 체크 후 toast 실행
    - 실행 후 `removeItem()`으로 초기화

**회고:**

- 상태 유지가 필요한 UI 메시지는 서버나 클라이언트 측 storage를 활용해야 함.
- sessionStorage는 탭 간 공유되지 않아 안전하며, `toastAlter()` 등 사용자에게 중요한 메시지 전달에 적합함.
